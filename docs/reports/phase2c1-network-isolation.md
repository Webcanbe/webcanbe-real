## Threat model and answers established before implementation

**Attacker:** an imported project's browser JavaScript and all its DOM, observations, routes and network requests. A hostile project can call native APIs without asking for camera or microphone access. Imported config, manifests, locks and assets are also untrusted data; Node-side uploaded code still cannot execute in the trusted compiler/editor process. Trusted components are the operator/editor API, project registry, source transaction implementation, platform dependency profile, and an eventual separately verified execution supervisor and OS boundary. The current local model assumes private project storage, not a hostile process concurrently writing the host filesystem.

**Invariant:** arbitrary project code must not initiate networking outside its isolated execution job. This includes UDP, TCP, DNS, IPv4/IPv6, host/loopback/LAN/platform/internal/sibling services, and protocols that do not pass through Fetch. Required display/input exchanges must be mediated by the trusted supervisor and authorized viewer; they must not provide project code with a URL proxy, signaling relay, CDP port, platform credentials, or mutation authority. Rendering pixels to the requesting user is intentional preview output, not permission for project-originated external networking. A strict mode cannot silently fall back to ordinary client JavaScript execution.

1. **Can standards-based browser controls alone guarantee zero egress for arbitrary JavaScript in supported end-user browsers? No supported guarantee was established; the currently validated Chromium family supplies a direct counterexample.** JavaScript enabled in an opaque, CSP-constrained, separate-origin frame sent UDP to the controlled receiver. This is not a claim about every conceivable future browser implementation. Firefox/WebKit/Safari have no acceptance evidence here; absence of those tests cannot broaden support. Disabling JavaScript would prevent the requested arbitrary JavaScript application from executing and is not a compatibility solution.
2. **Does CSP alone cover RTCPeerConnection/RTCDataChannel? `connect-src` is not a WebRTC firewall.** The current CSP3 working draft defines a separate `webrtc 'block'` directive and WebRTC integration; therefore a blanket statement that the specification has no RTC mechanism would be inaccurate. The tested browsers report that directive as unrecognized and still send packets. Draft text does not establish interoperable enforcement or close every egress path. The specification lists fetch, XHR, EventSource, beacon and WebSocket under `connect-src`. [CSP3 connect-src](https://www.w3.org/TR/2026/WD-CSP3-20260813/#directive-connect-src), [draft webrtc directive](https://www.w3.org/TR/2026/WD-CSP3-20260813/#directive-webrtc).
3. **Do Permissions Policy, sandbox or origin separation block data-channel networking? Not in the reproduced policies.** Camera/microphone denial was observed while `createDataChannel`, offer creation and supplied remote ICE candidate processing still caused networking. A diagnostic `Permissions-Policy: webrtc=()` was unrecognized. The opaque envelope confined the tested self-navigation, but did not block RTC. Origin separation protects access to other origins; it does not deny sending packets. The HTML sandbox's origin flag blocks cookie/storage/DOM access; its script permission is not a networking allowlist. [HTML sandbox flags](https://html.spec.whatwg.org/multipage/browsers.html#sandboxing), [Permissions Policy feature registry](https://github.com/w3c/webappsec-permissions-policy/blob/main/features.md). WebRTC explicitly describes cross-origin communication and data-channel exchanges without user involvement. [WebRTC security considerations](https://w3c.github.io/webrtc-pc/#privacy-and-security-considerations).
4. **Correct architecture:** execute all strict untrusted browser JavaScript inside an OS-controlled browser/runner/network environment. Keep the native browser sandbox. Transfer immutable compiled bytes into that environment, and return mediated raster output and bounded input/observations through a trusted controller. Moving only the HTTP server into a container while the application executes in the user's browser would leave the vulnerability intact.

The inherited Blob/HashRouter mode is an authorized-local compatibility workflow with its existing qualified security notice, not a strict hostile-code sandbox. Router-import detection is a compatibility gate, not a security boundary. The future strict admission policy must cover **all** imported JavaScript, regardless of router or transport.

Each run creates a fresh browser profile and owned listeners and closes them in `finally`. Parent canaries are synthetic. Collector ports and origin ports are not included in final new evidence. Final results: Chromium **153.0.8010.12** and installed Chrome **152.0.7977.83** each complete all five modes. Every restricted mode produces **34 UDP packets**: 3 STUN, 6 TURN and 25 supplied-candidate ICE packets. All collector positive controls and opaque-access denials hold. These are two Chromium-family builds, not cross-engine certification.

The same page code runs as an unrestricted positive control and under CSP, Permissions Policy, draft RTC policy, and an opaque confinement envelope. Positive controls receive fetch, WebSocket upgrade, EventSource, beacon, image and child-frame requests plus RTC-triggered UDP. Restricted modes receive no tested HTTP/resource requests but **do receive UDP**. Parent DOM/storage/cookie access is denied; restricted own storage/cookie access is denied; the preview hostname receives no parent host-only cookie.

RTC probes create real native `RTCDataChannel` objects and initiate STUN, UDP TURN and ICE connectivity checks using a supplied loopback remote candidate. They do not patch/delete constructors, require media permissions, or fetch signaling from the restricted page. The receiver records packets; **complete DTLS/SCTP application-payload delivery is not claimed**. Packet emission alone disproves zero egress. Per-protocol exhaustive IPv6/DNS/TURN-TCP coverage and a complete peer payload exchange remain requirements for a future controlled-provider acceptance harness; this counterexample matrix is not that harness.

## Smallest controlled-execution foundation

`src/webcanbe-engine/runtime/controlledPreview.ts` adds `ControlledPreviewTransport`, an internal `ProjectRunner` interface and immutable artifact snapshots. **No concrete execution provider is installed, no HTTP route instantiates this transport, and no existing endpoint returns its executable artifacts.** Its default is unavailable. Test doubles are defined only in the tests and establish broker behavior, not OS isolation.

- The trusted caller must supply the existing project/session preview capability. Generation IDs, source revisions, origins, URL knowledge, client flags and supplied isolation claims confer no authority. Extra start fields, external-network requests and nonlocal navigation are rejected. The fixed server-owned network capability is `external: deny`; no external networking grant is implemented.
- The compiler's HTML and every file path, MIME type and byte sequence become a copied, frozen snapshot with a deterministic SHA-256 digest. Mutable `Buffer`/`Map` references are not retained. The existing source revision still governs source mapping and transaction freshness. It covers `src`, not every public/config input: the compiled artifact digest therefore separately binds the exact bytes to execute. Tests change a public SVG without changing the source revision and verify a different snapshot digest. This is an immutable **build output** identity, not a claim of an atomic full-filesystem snapshot or complete input-provenance attestation.
- Each job gets a unique internal `.preview.invalid` origin and generation. Artifacts, route, revision and expiry go only to the server-injected provider. No project root, source-write capability, operator key or privileged cookie goes into the job. The returned presentation descriptor contains only raster transport, generation, revision and expiry; it contains no executable HTML, app URL, bootstrap ticket or artifacts.
- The minimal output interface accepts bounded PNG screenshots from a trusted screenshot encoder. It rejects HTML/SVG/URLs and invalid type/dimension headers. Header checks are **not** a complete PNG sanitization/decoder security proof; the future provider must own screenshot encoding and enforce allocation limits. Input is limited to bounded pointer interaction and validated local navigation. There is no evaluate-JavaScript, arbitrary URL, source-write or generic RPC input.
- The broker reauthorizes current project/session/revision/generation state before dispatch and after asynchronous operations. It copies validated routes/input before awaits, serializes operations, discards stale output, invalidates replaced generations and sweeps revocations independently of browser callbacks. Expiry is bounded by the source lease and a one-minute prototype job lease. Pending startup consumes capacity until a late handle is closed. Cleanup failure quarantines the transport. Closed instances cannot restart.
- Abort/close and lifecycle double tests prove the **broker calls the required cleanup**, not that an OS process died. A real provider must enforce its own process-tree kill, time/memory/CPU limits, artifact/profile/IPC deletion, pending-start cancellation, crash/parent-loss teardown and deadline even if the editor event loop stalls. Shutdown of this foundation can return while an aborting startup is still pending; that slot is retained and any late handle is closed. No production process-supervision guarantee is claimed.

The existing adapter, bridge message validation, editor UI, registry write authorization, transaction/diff/undo/redo/export pipeline, sandbox permissions and runtime dependency profile are unchanged. A preview observation or pointer action cannot authorize source writes. The current dormant HTTP listener remains a diagnostic prototype with its original read-only ticket/cookie checks; it is not reused as an externally accessible strict artifact endpoint.

## Required provider and browser-facing architecture

The intended first provider is a local Linux VM/network-namespace job (or equivalently verified environment), with no external network interface/default route/DNS path, no host networking/socket mounts, no sibling/platform service, a private browser profile and native browser sandbox retained. Supply artifacts and control the browser through supervisor-owned pipes. Handle HTTP navigation/assets inside the job, either by a job-local artifact service or bounded request fulfillment; fulfillment/interception is transport plumbing, never the network security boundary. Keep the control endpoint inaccessible to renderer code, and prohibit external self-navigation, popups, downloads, clipboard/host integrations and any generic proxy or logging callback that could become an exfiltration path.

The browser-facing viewer must remain on a separate origin and, for hosted deployment, a separate cookie site outside platform cookie scope. It runs platform-owned display code and renders encoded pixels, not uploaded JavaScript or DOM replay. It receives no WebCanBe mutation authority or privileged platform cookies. An authenticated broker must authorize every display/input connection against the project/session/generation; an unguessable URL, CORS, localhost, `Sec-Fetch-*` or a client assertion cannot replace that check. Existing source writes continue exclusively through the authorized editor/server transaction path. Validated bridge observations may later be carried over the supervisor channel for source selection; integrating that channel and the viewer is still outstanding.

External project networking must be an explicitly authorized, separately enforced project capability. It is denied in this foundation. A future network-enabled mode requires its own server-owned grant, destination/protocol policy and internal-address restrictions; a preview transport choice must never grant it accidentally. The strict mode retains complete network denial independent of CSP/RTC support in the user's browser.

Local audit found Darwin arm64, Node/npm, `sandbox-exec` and Chromium/Chrome. Docker, Podman, Lima, Colima and QEMU were absent on PATH; no suitable installed VM app/provider was established. The prior macOS outer network sandbox failed with Chromium's native sandbox retained. The Node export sandbox is not a browser isolation provider. That failed approach was not revived by disabling the native sandbox. No paid service, account, purchase, infrastructure installation, public deployment or unsafe browser flag was required or used.

**Missing proof:** a concrete provider running the application successfully with native sandbox retained while positive-control-validated OS/network probes fail across WebRTC, fetch/WebSocket/EventSource, resources/navigation, DNS/IPv4/IPv6, host/internal/sibling destinations; process/profile/IPC isolation, restart/expiry/revocation and cleanup under real crashes; an authenticated separate-origin raster viewer and broker; and the complete real BrowserRouter editor source workflow. The foundation does not turn these obligations into a boolean attestation or a PASS.
